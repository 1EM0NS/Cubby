# M0 命中测试证据

> 这是 `Cubby.App --selftest` 在真机上跑出来的原始报告，回答 issue #1：
> 「盒子区域可点、其余区域点击穿透」是否成立。
>
> 复现方式：
> ```powershell
> dotnet build -c Release
> .\src\Cubby.App\bin\Release\net8.0-windows\Cubby.App.exe --selftest
> ```
> 报告会写到 `src\Cubby.App\bin\Release\net8.0-windows\artifacts\`，退出码 0 表示全部通过。

## 测试设计

被测对象与一个**自建的受控背景层**对打，不依赖用户桌面状态：

1. 背景层铺满显示器并置顶，被测浮层随后置顶（后置顶者在上），于是背景层就是浮层正下方的那一层；
2. 用 `WindowFromPoint` 判断「这个坐标上的点击会被谁收到」（它与真实鼠标路由共用同一套命中测试）；
3. 再注入一次真实左键，看**应该收到的那一层是否真的收到了**——这是双向印证，不是只看一个信号。

采样点共 5 个：两个盒子中心（期望被浮层拦截），三个透明区域（期望放行给背景层）。

## 测试环境

- OS：Microsoft Windows 10.0.19045
- .NET：8.0.31（x64 进程）
- 显示器：2560×1440，DPI 缩放 1.25
- 命中区域（物理像素）：(75,100)-(600,475)、(75,525)-(600,850)

## 结论

1. **issue #1 有答案了**：WPF `AllowsTransparency` 窗口在 alpha=0 处**确实放行点击**，方案 A 成立，**不需要**降级到 `SetWindowRgn`。
2. 两个方向都被真实注入的点击证实：盒子内被我们拦截，盒子外穿透到下层。
3. 方案 B 同样有效，保留在代码里作为对照组与备选。

## 本次测试的边界（不要过度解读）

- 受控背景层与被测浮层同属本进程。窗口管理器的命中测试只看窗口形状与逐像素透明度，与进程归属无关，因此结论对第三方窗口同样成立；但**与 Wallpaper Engine 互动壁纸的端到端表现无法自动化**，仍须按诊断面板中的步骤人工确认。
- 置底（issue #2）、Win+D 后的恢复、多显示器与 DPI 切换都**不在**本测试覆盖范围内。
