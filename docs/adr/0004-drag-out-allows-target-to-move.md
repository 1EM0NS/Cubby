# ADR-0004：拖出时只提供 CF_HDROP，允许目标自行复制或移动

- 状态：已接受
- 日期：2026-09-19
- 对应原则：P4

## 背景

issue #8 要求「从盒子拖到资源管理器能落地」，并写明「拖出默认仍为移动或按设置询问」。
P4 规定**文件实体永不移动，只保存引用与展示位置**。两者在字面上有冲突，必须先定清楚边界。

## 决策

1. Cubby 拖出时**只**在 `DataObject` 里放一条 `CF_HDROP`（WPF 的 `DataFormats.FileDrop`）路径，
   允许的效果是 `Copy | Move`；
2. **Cubby 自身不执行任何文件操作**——不调用 `File.Move/Copy/Delete`，不发 `CFSTR_PREFERREDDROPEFFECT`
   之类的指令去"要求"目标怎么做；
3. 是否复制、移动、做成快捷方式，由**目标窗口（资源管理器）与用户的修饰键**决定，与真实桌面图标的行为一致；
4. 拖放返回 `Move` 时意味着源文件已被目标移走、条目引用失效，此时把该条目**移出盒子**
   （仍然只是删掉引用，不做任何磁盘操作）。

## 理由

1. P4 约束的是**Cubby 自己**不许移动用户文件，而不是禁止用户通过拖拽把文件挪走——
   后者是 Windows 桌面的固有语义，禁掉反而变成"盒子里的图标拖不动"；
2. 提供 `CF_HDROP` 是唯一的系统标准通道，自己实现一套复制逻辑既多写代码又更容易出错；
3. `Move` 后保留失效引用会让盒子长期显示"打不开的条目"，移出是更诚实的处理。

## 后果

- 拖出到资源管理器后文件是否还在原处，取决于用户的操作意图，不取决于 Cubby；
- 若将来要做"移出后按设置询问"（issue #8 里提到的另一种语义），只需在 `StartDragOut` 里改
  对返回效果的处理，不涉及任何磁盘 API；
- CI 守卫继续拦 `LVM_SETITEMPOSITION*` / `LVM_ARRANGE`，与本条无关。
