> 本文件是 M0 阶段三个关键结论的原始证据：命中测试（issue #1）、置底（issue #2）、
> 钩子链（issue #3 / #4）。所有数据都是真机跑出来的，不是推断。
>
> 复现方式（在仓库根目录）：
> ```powershell
> dotnet build -c Release
> # 1. 命中测试（自动）
> .\src\Cubby.App\bin\Release\net8.0-windows\Cubby.App.exe --selftest
> # 2. 钩子链基线（此时先不要启动 Cubby）
> .\tools\HookProbe\bin\Release\net8.0-windows\HookProbe.exe --out artifacts\hookprobe-baseline.json

> .\tools\HookProbe\bin\Release\net8.0-windows\HookProbe.exe --baseline artifacts\hookprobe-baseline.json
> ```

## 一、命中测试：盒子区域拦截，其余穿透（issue #1）

被测对象与一个**自建的受控背景层**对打，不依赖用户桌面状态：

1. 背景层铺满显示器并置顶，被测浮层随后置顶（后置顶者在上），于是背景层就是浮层正下方的那一层；
2. 用 `WindowFromPoint` 判断「这个坐标上的点击会被谁收到」（它与真实鼠标路由共用同一套命中测试）；
3. 再注入一次真实左键，看**应该收到的那一层是否真的收到了**——双向印证，不是只看一个信号。

**命中区域（物理像素）**：(75,100)-(600,475)、(75,525)-(600,850)

### 方案 A：逐像素 alpha → PASS

| 采样点 | 期望 | 实际命中层 | 注入点击 | 浮层收到 | 背景层收到 | 判定 |
|---|---|---|---|---|---|---|
| 盒子 A 中心 | 拦截 | 被测浮层 | 是 | 是 | 否 | **PASS** |
| 盒子 B 中心 | 拦截 | 被测浮层 | 是 | 是 | 否 | **PASS** |
| 盒子外 · 右中 | 放行 | 受控背景层 | 是 | 否 | 是 | **PASS** |
| 盒子外 · 右下 | 放行 | 受控背景层 | 是 | 否 | 是 | **PASS** |
| 盒子外 · 中下 | 放行 | 受控背景层 | 是 | 否 | 是 | **PASS** |

### 方案 B：窗口区域 → PASS

5 个采样点全部 PASS，数据同上。

**结论**：WPF `AllowsTransparency` 窗口在 alpha=0 处确实放行点击 → **方案 A 成立，不需要降级到 `SetWindowRgn`**。

**边界**：受控背景层与浮层同属本进程。窗口管理器的命中测试只看窗口形状与逐像素透明度，与进程归属无关，因此结论对第三方窗口同样成立；置底、Win+D、多显示器不在本测试覆盖范围内（另见下文与 M1）。

## 二、置底：在应用窗口之下、桌面层之上（issue #2 / A4）

`ZOrderProbe --assert-behind --exe Cubby.App --title "Cubby 浮层"` → **退出码 0（PASS）**

```
== 置底断言（pid=22304，标题过滤=Cubby 浮层）==
   被断言的窗口：0x00140540 class=HwndWrapper[Cubby.App;;...]  visible=True  rect=(0,0)-(2048,1152)
   位置：第 17 位（0 为最顶层），可见顶层窗口共 21 个
   它下方共 3 个窗口
PASS：它下方只有桌面层 / 任务栏 / 同进程窗口 / 屏幕外窗口，没有压住任何应用窗口。
```

同一时刻的窗口链快照（节选）：

```
    0  Shell_TrayWnd          pid=11360  rect=(0,1112)-(2048,1152)   [任务栏]
    1  HwndWrapper[Cubby.App] pid=22304  rect=(694,256)-(1354,856)   ← 诊断面板（普通窗口）
    2  Chrome_WidgetWin_1     pid=4544   rect=(138,94)-(1907,1068)   [应用窗口]
   ...
   17  HwndWrapper[Cubby.App] pid=22304  rect=(0,0)-(2048,1152)      ← 浮层（被断言对象）
   18  WorkerW               pid=11360  rect=(0,0)-(2048,1152)      [桌面层]
   19  WorkerW               pid=11360  rect=(0,0)-(2048,1152)      [桌面层]
   20  Progman               pid=11360  rect=(0,0)-(2048,1152)      [桌面层]
```

**推论**：浮层位于所有应用窗口之下、桌面层之上，因此它**不会遮挡任何应用窗口**；同时因为它在图标层之上，盒子能盖住桌面图标区域并接收那里的点击。

## 三、钩子链：没有吞掉鼠标消息（issue #3 / #4 / A1 / A3）

`HookProbe` 把自己挂在低级别鼠标钩子链的末端，注入 10 次左键，数自己收到多少条按下类消息。

**为什么必须做基线对比**：第一次跑的时候发现「注入 10 次只收到 8 次」，差点误判成"我们的程序在吞消息"。
实际上**基线状态（Cubby 完全没运行）同样只收到 6 次**——本机装了 Wallpaper Engine（窗口列表里能看到它的
`WPEUI` 窗口），它自己挂在钩子链上游并吞掉了一部分点击。所以绝对计数在本机毫无意义，
唯一有意义的判据是「被测程序运行时，不差于它未运行时的基线」。

| 项 | 基线（Cubby 未运行） | 被测运行中 |
|---|---|---|
| 注入左键次数 | 10 | 10 |
| 按下类消息 | 6 | **8** |
| 抬起消息 | 10 | 10 |
| 鼠标移动 | 22 | 52 |

**判定：PASS（退出码 0）** —— 被测状态下的观测结果不差于基线（按下类 +2，抬起 0），
说明 Cubby 没有让任何鼠标消息消失。这与设计一致：本程序根本不注册鼠标钩子，只被动接收落到自己窗口上的点击。

**边界**：本探针只能证明「整条钩子链」没有被 Cubby 影响，无法把丢消息归因到具体程序；
归因方法就是本节的基线对比。
